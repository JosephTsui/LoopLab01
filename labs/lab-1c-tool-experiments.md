## 實驗 A — 串行 vs 並行讀取

**目標：** 比較一次讀一個檔案 vs 同時讀五個檔案的行為差異

**測試對象（5 個檔案）：**
- `README.md`
- `CLAUDE.md`
- `.claude/settings.json`
- `experiments/sample.js`
- `reports/file-summary.md`

### 測試 1：串行讀取

5 次 Read 呼叫，分散在 5 個獨立訊息中依序執行。

| 呼叫順序 | 檔案 | 結果 |
|---------|------|------|
| 1 | `README.md` | Wasted call（本輪稍早已讀過） |
| 2 | `CLAUDE.md` | 正常回傳 |
| 3 | `.claude/settings.json` | Wasted call |
| 4 | `experiments/sample.js` | Wasted call |
| 5 | `reports/file-summary.md` | 正常回傳 |

- **往返次數：5**
- **實際讀取：2**（其餘 3 個快取命中）

### 測試 2：並行讀取

5 次 Read 呼叫全部放在同一個訊息中同時送出。

| 結果 |
|------|
| 5 次全部 Wasted call（串行測試剛讀完，全部命中快取）|

- **往返次數：1**
- **實際讀取：0**（全快取命中）

### 比較結論

| 指標 | 串行 | 並行 |
|------|------|------|
| 訊息往返數 | 5 | 1 |
| 牆鐘時間（wall-clock） | 串行疊加 | 最慢單一檔案的時間 |
| 適用場景 | 後一個 Read 依賴前一個結果 | 檔案之間無依賴關係 |

**Claude 的決策原則：** 若多個 Read 互相獨立（不需要用 A 的結果決定讀不讀 B），則自動選擇並行，節省往返次數。

**額外觀察：快取機制**
系統會追蹤本輪對話中已讀取且未變動的檔案，再次讀取時直接回傳快取結果並標示 "Wasted call"，不消耗額外工具配額。這是 Agent Loop 的效率保護機制。

## 實驗 B — Agent 委派

**目標：** 觀察主代理如何把任務交給子代理，以及結果如何被使用

**任務：** 統計 `labs/` 目錄下所有檔案的總單詞數

### 觀察結果

| 項目 | 數值/觀察 |
|------|---------|
| 子代理用時 | 7.15 秒 |
| 子代理 token 消耗 | 15,954 |
| 子代理工具呼叫數 | 1 次（Glob 或 Bash 列目錄） |
| 子代理回傳結果 | 「目錄為空，無檔案可統計」 |
| 主代理行為 | 收到文字結果後直接繼續，未再讀取 labs/ |

### 委派流程分析

```
主代理
  │
  ├─ Agent 工具呼叫（送出任務描述）
  │       ↓
  │   子代理（獨立 context）
  │     ├─ Glob / Bash：列出 labs/ 內容
  │     └─ 回傳：「目錄為空」
  │       ↓
  └─ 接收文字結果 → 繼續後續步驟
```

**關鍵觀察：**
- 主代理完全不知道子代理內部用了哪些工具，只看到最終回傳的文字
- 子代理有獨立的 context window，不共用主代理的對話記憶
- 委派適合用於：耗時的搜尋任務、需要隔離 context 的大量讀取、可平行的獨立子任務

---

## 總結：何時用哪種模式

| 情境 | 推薦做法 |
|------|---------|
| 讀取多個無依賴關係的檔案 | 並行 Read（同一訊息） |
| A 的結果決定要不要讀 B | 串行 Read（分開訊息） |
| 任務龐大、需要保護主 context | Agent 委派 |
| 任務簡單、需要即時結果 | 主代理直接執行 |
